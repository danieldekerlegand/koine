## Codebase Patterns
- **Guards to run after any doc/spec edit:** `node scripts/check-doc-integrity.mjs` (relative links +
  anchors + the 3 status-table mirrors), `node scripts/check-tasklist-categories.mjs`, and the merge
  gate itself: `.chief/verify.sh --run <changed files…>` (it selects gates from paths; `--plan` reads
  STDIN). The *Current state* prose in CLAUDE.md is a FOURTH mirror that is **not** checked — update
  it by hand when a spec version moves.
- **A new doc must be linked from `docs/README.md`** — the repo's stated rule is "a document not
  linked here does not exist". check-doc-integrity does not enforce it; the map is the contract.
- **Version discipline in this repo is deliberate and quotable.** KCB lands additive normative text
  as a PATCH (0.4.6 added six §3.1 clauses; 0.4.7 added §4.2) because **0.5.0 is reserved** for
  §2.2's standalone-manifest removal; KMI's 0.4.0 is likewise spent on the EDL removal. Check what
  the next minor is already spoken for BEFORE choosing a bump.
- **Relations are immutable:** never edit a signature in `registry/relations.tsv` — mint a new name
  (precedent: KFT 0.6.0's `continues`).
- **KINP owns identifiers/worlds/resolution semantics**; other specs reference, never redefine. That
  rule decides where a cross-spec fold lands, and it is how a fold avoids adding a gate to a spec
  that is close to promotion (KGP).

**Learnings for future iterations**
- **No schema twin needed here, and that is worth stating rather than assuming.** Nothing in
  `schemas/` models the KMI §2 asset envelope or a KINP equivalence link, and
  `participant-self-description.schema.json` references the KCB manifest **by pointer only**
  (ADR-0007 d7), so an added `params` field never reaches it. `provenance.schema.json`'s
  `$defs.license` / `$defs.egress` are vocabularies KMI *reuses*; they were not altered.
- **Watch the "this section is additive — no field is added" sentences.** Both KCB §3.1 and KMI §7.1
  opened with one, and both became false the moment a fold added an optional field. Grep the section
  you are folding into for its own additivity claim before you add anything.
- **A fold has to correct the predictions the scenario made about it.** `e2e-multi-authority.md`'s
  *What a clean pass would license* predicted 0.5.0 for KCB and "0.5.0 or a patch that adds no
  field" for KMI; both were superseded by the reserved-minor rule. Leaving them would have put the
  scenario in direct conflict with the spec headers, and no guard checks that.
- **Anchors in `specs/identity.md` §11 are inside a numbered list** — continuation lines carry a
  3-space indent, so an exact-match edit fails unless you include it.
- The disposition doc from US-1 was accurate throughout; every landing zone it named was the right
  one, and the two scenario-framing corrections it recorded both held when the clauses were edited.
